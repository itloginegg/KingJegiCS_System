## 1. Dashboard Overview & Calendar UI (Frontend & Backend)

**Verified current state.** `AdminDashboardPage.tsx`'s Overview calendar (~line 1936) is partly real and partly fabricated. The day cells that list bookings (`dayEvents = reservations.filter(r => r.eventDate === dateStr && ...)`) are driven by real booking data. But the "conflict"/lock indicator is not: `conflictDates` (~line 908) flags any date with `>= 2` active reservations — a threshold invented on the frontend that has nothing to do with the backend's actual rule. The real rule lives in `Calendarday.RecalculateLock()`: `IsLocked = IsManuallyLocked || ConfirmedCount >= MaxCapacity`, where `MaxCapacity` defaults to `SystemSettings.DefaultMaxCapacity` (3) and only **Confirmed** bookings count, not Pending. There is currently no way for the frontend to see this real state at all: `DTOs/Calendardaydtos.cs` already defines `CalendarDayResponseDto` and `SetDayLockDto` (manual lock/unlock), but **no controller anywhere exposes them** — grep confirms zero usage outside that DTO file. There's also no admin action to manually lock/unlock a day anywhere in the UI.

**Fix:**
- Backend: add a `CalendarDaysController` (or actions on an existing one) exposing (a) a bulk read for a date range — `GET /api/CalendarDays?from=&to=` returning `CalendarDayResponseDto[]`, reusing the existing unused DTO — and (b) an admin-only lock/unlock action consuming the existing `SetDayLockDto`, which should write `IsManuallyLocked` and call `RecalculateLock()`. `Owner,Assistant` only, matching every other admin-mutation endpoint's `[Authorize(Roles = "Owner,Assistant")]`.
- Frontend: replace `conflictDates`'s invented threshold with real per-day state from the new endpoint — `IsLocked`, `ConfirmedCount`/`MaxCapacity`, `IsManuallyLocked` — and add whatever UI you need for an admin to toggle the manual lock (a click on a day cell opening a small confirm, or similar — match the existing `adm-cal-*` classes and card conventions). The same real data should also correct `BookingPage.tsx`'s and `LandingPage.tsx`'s calendars if they're meant to reflect true lock state — worth confirming scope: LandingPage's calendar (~line 123, "Demo-only reserved dates so the calendar has something to show") is currently fully mocked and separate from this fix; decide whether it's in scope here or a later pass.

**Monthly Sales Report.** The Overview page's existing "Revenue Trend" chart (~line 1919, labeled "Last 6 Months") is also fake — `REVENUE_BY_MONTH` (~line 105) is a hardcoded array, not derived from real `Payment`/`Invoice` data. Building a real Monthly Sales Report means: a new backend aggregation (sum of successful payments — same `Success`/`PartiallyRefunded`/`Refunded` net-of-refund logic `Invoiceservice.GetPaidTotalAsync` already uses — grouped by month) exposed via a new endpoint, and a frontend module that replaces or sits alongside the current chart with real numbers.

**AI-generated summary, as a finishing touch.** The backend already has a Gemini-backed `Assistantservice` (Slice C) — recommend reusing that plumbing (a focused prompt over the real aggregated sales numbers, called server-side when the report is requested) rather than standing up a second AI integration. Confirm this approach before building; it's the only sensible reuse path given what already exists, but it's still a real design choice (new endpoint? computed inline with the sales report response? cached, since it costs a Gemini call each time?).

## 2. Contract Generator

**Verified: nothing exists for this today**, no backend model/service/controller, no frontend UI. The only relevant precedent in the codebase is the Invoice "Print" feature in `CustomerDashboardPage.tsx` (~line 478: `<button onClick={() => window.print()}>Print</button>`, paired with a `@media print` block scoping to `#cds-invoice`) — a pure client-side, browser-print approach with **no PDF library anywhere in the stack** (confirmed against `System_ApiTest.csproj` — no QuestPDF/iText/PdfSharp/etc.).

**Decision to confirm before building:** does "generate a contract" mean (a) a nicely formatted HTML view the admin can print/save-as-PDF from the browser, matching the existing Invoice-print convention exactly, with zero new dependencies — or (b) a real PDF file the backend produces and can store/attach/email, which would need a new server-side PDF library and is a bigger addition? Recommend (a) unless there's a concrete need (e-signature, emailing the contract, archiving outside the browser) that requires a durable server-generated file — state which is wanted before building.

**Anchor point, verified:** `AdminDashboardPage.tsx`'s Bookings tab already renders a "Generate Invoice" button that only appears when `r.status === 'Confirmed'` (~line 2107–2116). Add "Generate Contract" right alongside it, same visibility rule ("for every 'Confirmed' booking," per the ask). The data needed — booking, customer, package/menu/rental/service lines, invoice totals — is already available via the existing `GET /api/Bookings/{id}` detail endpoint; no new read endpoint should be needed for the contract's content itself, only for whichever generation approach is chosen above.

## 3. Bug Fixes & Data Syncing

**3a. "Booking History" — reframed: this is a missing feature, not a mismatch to fix.** A thorough search (`grep -rin "history"` across every page, component, and API client) turns up nothing relevant in `AdminDashboardPage.tsx` — no booking-history UI exists there at all, so there's nothing currently "displayed" that could be out of sync with the backend. The backend side is fully built and unused: `GET /api/Bookings/{id}/history` (`Owner,Assistant`-only) returns `BookingHistoryResponseDto[]` with each row's `SnapshotJson` (a serialized before-state snapshot written by `Bookingservice.WriteHistorySnapshotAsync` on every mutating call). Nothing in `bookingApi.ts` even calls this endpoint today.

Treat this as building the feature for the first time: add a client function for `GET /api/Bookings/{id}/history`, and a revision-timeline UI (likely inside a new booking-detail view in `AdminDashboardPage.tsx`, since none currently exists — see item 2's contract button for where a "view detail" entry point would naturally live too) that parses each row's `SnapshotJson` and renders what changed, who changed it (`ChangedById`, null = customer/system), and when.

**3b. Notifications not displaying — needs disambiguation before fixing, verified there's no dedicated notification UI to have failed.** A full search (`grep -rn "notification"` across pages/components/api) finds exactly one hit outside the generic toast system: a code comment in `CustomerDashboardPage.tsx` about Slice D. There is no notification bell, panel, or feed anywhere in the app — the only notification-shaped thing that exists is the generic `ToastViewport`/`useToasts` success/error/info system (`components/ui/Toasts.tsx`), which **is** wired up and mounted in both `AdminDashboardPage.tsx` and `CustomerDashboardPage.tsx`.

This means "notifications not displaying" is one of two very different problems, and building the wrong fix wastes the effort:
- **If you mean the toasts** (the "Booking confirmed," "Payment recorded," etc. pop-ups): audit every `notify(...)` call site against the actions that should trigger one, and check for silent failures (a thrown error before `notify()` is reached, a toast that fires but is immediately dismissed by a re-render, z-index/stacking issues). This is a real, findable bug if it exists — confirm reproduction steps before assuming a cause.
- **If you mean Slice B/D's backend notification system** (email reminders, proactive assistant nudges) should be visible inside the app: that's new scope, already flagged as a gap in `KingJegi_frontend_ui_build_prompt.md` — Slice B is email-only with no read endpoint, so there is nothing in-app for the frontend to fetch and display even in principle. Building this means a new backend read endpoint first (what would even populate a notification feed?), not a frontend fix.

Confirm which one this is (or reproduce the toast failure concretely) before starting — "troubleshoot" implies (a), but the codebase has no in-app notification feed at all, which is why I'm flagging (b) as the likely actual intent if toasts turn out to be working fine on inspection.

**Build, matching house conventions** (see `Services/Auditlogservice.cs`/`Systemsettingsservice.cs` for the simplest reference shape, and any `[Authorize(Roles = "Owner,Assistant")]` controller for the moderation-endpoint pattern):
