## 1. Role-based notification system

**Good news first: the UI shell is already built and needs no structural changes.** Both `CustomerDashboardPage.tsx` (~line 1436) and `AdminDashboardPage.tsx` (~line 2451) already have a working bell icon, unread badge, dropdown panel, mark-one-read, and mark-all-read, all wired to the real `NotificationsController`/`api/notificationsApi.ts`. Critically, the rendering is fully generic — it displays whatever `title`/`body` the backend sends per row — so adding new notification kinds requires **zero** frontend UI work; the bell will pick them up automatically.

**The actual gap is entirely backend, and it's a real one.** `Services/Notificationfeedservice.cs` only surfaces the kinds the existing `NotificationWorker` already emails: `PaymentDueSoon`, `PaymentOverdue`, `PaymentOverdueDigest` (staff), `BookingConfirmed`/`BookingCancelled` (customer-only today), and `RentalLowStock` (staff). None of the events on your list exist as tracked kinds at all: staff-facing new-booking-created, refund-requested, payment-made, rental/food-delivery-item-added, or incoming-chat-message; customer-facing refund-approved/declined, payment-confirmed, or booking-completed. `BookingCancelled` exists but is customer-only in `Notificationfeedservice`'s `StaffKinds`/`CustomerKinds` split — staff don't currently get it either.

**Why this needs a design decision, not just new enum values:** the existing system is architecturally a *poller* — `NotificationWorker` wakes up on an interval and checks ongoing state ("is this milestone still unpaid N days later," "is stock still low"). Every event on your list is the opposite: a discrete action that happens once, at a specific instant (a payment succeeds, a refund is requested, a rental is added). Polling can't detect "the moment a payment was recorded" — that has to be written the instant it happens, from inside the service method that does it. Recommend: extend `NotificationKind` with the new instantaneous kinds, and write a `Sentnotification` row synchronously from each relevant call site rather than from the worker — `Paymentservice.MarkSuccessAsync` (payment confirmed), `Paymentservice.RequestRefundAsync` + wherever an admin approves/denies a refund (both refund events), `Bookingservice.CreateAsync` (new booking), `Bookingservice.RequestCancellationAsync`/`CancelBookingAsync` (cancellation — write to staff kinds, unlike today's customer-only `BookingCancelled`), `Bookingservice.CompleteBookingAsync` (completed), `Rentalservice.AddRentalAsync` and `Bookingservice.AddMenuItemAsync`/`AddMenuTrayAsync` for `FoodDelivery` bookings (item-added), and `SupportController.SendAsCustomer`/`SendAsAdmin` (chat message, to whichever side didn't send it). Confirm this full kind list and the write-site approach before touching that many existing service methods — it's a wide but shallow change, and easy to under- or over-scope without agreeing the list first.

**Nice-to-have, confirm if in scope:** neither bell currently updates live — `loadNotifications` only runs on mount and when opened. The app already has three precedents for pushing live updates through the existing `PaymentHub` (`"PaymentUpdated"`, `"SupportMessage"`, `"AssistantNudge"`, all listened to via the SignalR connections already open in both dashboards) — adding a `"NotificationCreated"` broadcast alongside the new write-sites above would make the badge update without a manual refresh, following the exact same pattern rather than introducing a new transport.

## 2. Chat support file and image uploads

**Verified: today's support chat is text-only, end to end.** `Models/Supportmessage.cs` has only a `[MaxLength(4000)] Text` field — no attachment column of any kind. `SupportController`'s `SendAsCustomer`/`SendAsAdmin` bind `[FromBody] SupportSendDto`, which is JSON with just `Text`. `api/supportApi.ts`'s `sendSupportMessage` and `ChatWidget.tsx`'s `SupportPanel` match that — plain text send, no file input anywhere.

**Reuse the existing precedent, but note it doesn't fully cover the ask.** `Services/ImageUploadHelper.cs` (already used for `MenuItem`/`RentalItem` photos) validates and saves **images only** — `.jpg/.jpeg/.png/.webp`, 5 MB cap — to `wwwroot/images/{subFolder}/`. Your ask is "files and images," which is broader. **Confirm before building:** what file types beyond images should be allowed (PDFs? any document? anything at all?), and what size cap. Recommend either generalizing `ImageUploadHelper` into a broader helper with a configurable allow-list, or adding a parallel `FileUploadHelper` for non-image attachments saved under something like `wwwroot/uploads/support/` — don't just widen the existing image helper silently, since it's shared with the catalog-image upload paths.

**Build, once scope is confirmed:**
- Migration adding nullable attachment fields to `Supportmessage` (URL, original filename, content type) — a message needs to support text-only, attachment-only, or both.
- `SupportSendDto` gains an optional `IFormFile? Attachment`; `SendAsCustomer`/`SendAsAdmin` switch from `[FromBody]` to `[FromForm]` to accept multipart (mirroring how `MenuItemCreateDto`/`RentalItemCreateDto` already take an optional `IFormFile? ImageFile`).
- `SupportMessageDto` and `api/supportApi.ts`'s `SupportMessage` interface gain the attachment fields; `sendSupportMessage` needs a path that posts `FormData` instead of JSON when a file is attached.
- `SupportPanel` in `ChatWidget.tsx` gets an attach control, an image preview for image attachments, and a plain download link for anything else.

## 3. Frontend error handling — correcting the premise, then a real fix

**There is exactly one business-rule exception class in the backend, not several: `BookingRuleException`** (defined in `Services/Bookingservice.cs`). Three other exception types exist — `AssistantUnavailableException`, `EmailSendException`, `PayMongoException` — but they belong to unrelated subsystems (the Gemini assistant, SMTP, PayMongo) and are each already handled where they're thrown.

**More importantly: the wiring you're asking for already exists, application-wide.** Every controller catches `BookingRuleException` and returns `BadRequest(new { message = ex.Message })`. Every one of the app's API client files — there are now eleven of them (`bookingApi.ts`, `suggestionsApi.ts`, `assistantApi.ts`, `notificationsApi.ts`, `supportApi.ts`, `calendarApi.ts`, `customerAdminApi.ts`, `reportsApi.ts`, `testimonialsApi.ts`, `menuAdminApi.ts`, `rentalAdminApi.ts`, `serviceAdminApi.ts`, `paymentAdminApi.ts`) — implements the identical `readErrorMessage`/`{Area}ApiError` pattern that extracts that `message` and throws a typed error carrying it, which call sites then catch and pass to `notify('error', err.message)`. This isn't a gap; it's already the house convention, consistently applied, including in the newest files added since the last round of work.

**What's real: at least one call site doesn't follow the convention and silently swallows an error.** `CustomerDashboardPage.tsx`'s `BookingDetailModal`, in its detail-fetch effect (~line 205–216), does `catch (err) { console.error('Failed to fetch details:', err); }` — no `notify()`, so a failed `getBookingDetail`/`getPackageSelections` call leaves the customer looking at a modal that never populates, with zero explanation. That's a genuine, fixable bug.

**Recommended fix:** sweep every `catch` block in `pages/` and `components/` for the same shape (`console.error`-only, or an empty catch) and add `notify('error', ...)` consistent with everywhere else. I found one confirmed instance above; there may be more — a full sweep is cheap compared to guessing. If you already have a specific action in mind where an error currently goes unshown, give repro steps and start there instead of a blind sweep.

## 4. Payment routing flow

**Verified: this is a real, concrete gap, and it's more specific than "add a redirect."** Online/gateway payments already leave the SPA entirely — `CustomerDashboardPage.tsx` does `window.location.href = data.checkoutUrl` (~line 557–558) to send the customer to PayMongo's hosted checkout page. `PayMongoOptions.SuccessUrl`/`CancelUrl` (in `PayMongoOptions.cs`, documented example `https://yourfrontend/payment/success`) are exactly where PayMongo sends the browser back afterward — but **no frontend route matches that URL at all.** `routes/AppRoutes.tsx` has no `/payment/success` or `/payment/cancel` route; today a configured `SuccessUrl` would land on a page the SPA doesn't recognize and fall through to the catch-all (`<Route path="*" element={<Navigate to="/" replace />} />`), dumping the customer on the public homepage — not the dashboard, and definitely not the Payments tab.

**Fix:**
- Add `/payment/success` (and `/payment/cancel`, for the existing `CancelUrl`) routes/pages.
- Payment confirmation is asynchronous — `Paymentservice.MarkSuccessAsync` runs from PayMongo's server-to-server webhook (`ApplyGatewayPaidAsync`), which may not have finished the instant the browser's redirect lands, since the redirect and the webhook are two separate, unordered round-trips. Don't treat arriving on `/payment/success` as proof of success: show a brief "confirming your payment…" state and either listen for the existing `PaymentHub`'s `"PaymentUpdated"` broadcast (already used for exactly this purpose elsewhere) or poll the booking/invoice once or twice before declaring success, then route into `CustomerDashboardPage` with the Payments tab pre-selected.
- `CustomerDashboardPage`'s tab state always initializes to `'overview'` today — it needs a way to start on `'payments'` from outside, e.g. reading a `?tab=payments` query param or router `state` on mount.
- **Confirm scope:** does "immediately after a successful payment" also mean manually-recorded (cash/admin-entered) payments? Those never leave the SPA in the first place, so there's no redirect involved — just switching the already-open dashboard to the Payments tab right after `RecordAsync`/`MarkSuccessAsync` succeeds, which is a much smaller, purely in-SPA change than the gateway-return routing above. Say which (or both) you want.
