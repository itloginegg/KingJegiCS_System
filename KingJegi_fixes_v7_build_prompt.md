## 1. Backend Models & Logic (C# / .NET)

**1a. New `BookingType.RentalService` — this is a real, wide-reaching change, not a one-line enum add.** Today `Models/Booking.cs` (line 21) defines exactly two values: `FullService, FoodDelivery`. A "Rental Items Only" booking already exists as a *concept* in the frontend — `BookingPage.tsx`'s `'rentals'` service flow — but at the data level it's just a `FullService` booking with no package/menu selected (`handleCreateBooking`, line 358, hardcodes `bookingType: 'FullService'` for both the `'event'` and `'rentals'` flows). Adding a real third enum value means every place in the backend that currently branches on `BookingType` in binary (`== FoodDelivery` / else-assume-FullService, or `!= FullService` / else-assume-delivery-like) needs an explicit decision about which side `RentalService` falls on — a new third value doesn't safely "just work" against `if/else` logic written for two. I found these sites grepping the codebase:

- `Bookingservice.cs` line 280, inside `TryAutoConfirmOnReservationAsync`: `if (booking.BookingType != BookingType.FullService) return false;` — today this means only `FullService` auto-confirms when the reservation fee clears. If `RentalService` bookings should also auto-confirm on deposit (my read: they should — they're event/pickup-dated the same way), this line needs `RentalService` added explicitly, or rewritten as `!= FoodDelivery`.
- `Invoiceservice.cs` line 187, inside `BuildMilestonePlanAsync`: `if (booking.BookingType != BookingType.FullService)` routes anything else into a single lump-sum-due-on-event-date milestone plan (the delivery shape). Left unchanged, a `RentalService` booking would silently get treated as a delivery for billing purposes — one balance due on the rental date, no deposit/mid-payment milestones. Decide whether that's actually right, or whether rentals should get the same multi-milestone deposit plan as `FullService`.
- `Bookingservice.cs` lines 48, 83–92, 432–438, 529, 761 (inside/around `EnsureNotDeliveryAsync`, line 755): a cluster of `bookingType == FoodDelivery` branches controlling lead-time-before-event validation and the rule that blocks rental line-items from attaching to delivery bookings. Since `EnsureNotDeliveryAsync` already exists specifically to keep rentals off `FoodDelivery` bookings, it should be a no-op for `RentalService` (rentals are the whole point of that type) — but the lead-time rules (48, 83–92, 432–438) need an explicit answer: does a rental-only booking follow the event lead-time rule or the delivery lead-time rule? They're not identical today.
- `Suggestionservice.cs` and `Assistantservice.cs` (line 545) also branch on `BookingType` — the AI assistant's booking-type inference and the budget-suggestion engine's `MaterializeAsync` currently only ever produce `FullService` or `FoodDelivery`. Whether "Plan by Budget" or the chat assistant should ever be able to produce a `RentalService` booking is a separate product question (see item 2b below for the related frontend confusion) — I'd scope this out unless you want it.

**Recommend before building:** confirm the intended behavior for each bullet above (auto-confirm eligibility, milestone/billing plan, lead-time rule) — most naturally resolve to "treat `RentalService` like `FullService`" since it's the same event-dated, deposit-based booking shape minus a package, but that should be a stated decision, not an inferred one. Once confirmed, this becomes a mechanical pass: add the enum value, update each flagged branch, add an EF Core migration if anything besides the enum needs a schema change (the enum itself is stored as a string via `JsonStringEnumConverter`/EF's normal enum mapping, so likely no migration is needed for the enum alone — check whether `Booking.BookingType`'s EF configuration stores it as `int` or `nvarchar`; if `int`, appending `RentalService` last preserves existing stored values, don't insert it mid-list). Frontend: `BookingCreatePayload.bookingType` (`api/bookingApi.ts` line 43, currently `'FullService' | 'FoodDelivery'`) needs the new literal, and `BookingPage.tsx`'s `'rentals'` flow (line 358) should switch from sending `'FullService'` to `'RentalService'`.

## 2. Frontend UI/UX & State Management (React)

**2a. Booking Wizard Abandonment — the "delete instead of Draft" ask needs a new backend capability that doesn't exist, and the "warn on leave" ask runs into real browser/router limitations worth knowing about before you build the literal spec.**

**No delete capability exists anywhere today.** I searched both the controller and service:
```
grep -n "\[HttpDelete\]" Controllers/BookingsController.cs        → no matches
grep -n "DeleteAsync|RemoveAsync|HttpDelete" Services/Bookingservice.cs Controllers/BookingsController.cs  → no matches
```
This has to be built from scratch. The good news: `CreateAsync` doesn't call `WriteHistorySnapshotAsync` (history rows only get written on Submit/Confirm/Cancel/Complete), and a Draft has no `Invoice` yet (invoices are generated at Submit) — so a booking that's still sitting at Draft, never submitted, has no dependent history/invoice/payment rows to clean up, making a real hard delete of it safe and simple. **Scope the new endpoint tightly:** `DELETE /api/Bookings/{id}`, allowed only when `booking.Status == Draft` and the caller owns it (or is Owner/Assistant) — never allow deleting a Pending-or-later booking through this path, since those do have history/dependents by then.

**Decide the actual product intent first — literal "delete on any leave" removes a feature you may not want to remove.** Today, leaving mid-wizard leaves a Draft behind, and Draft bookings are visible and resumable from `CustomerDashboardPage`'s Bookings tab — i.e., "leave and come back later" is a legitimate, currently-working use case, not just clutter. Deleting unconditionally on every leave removes that entirely. Worth confirming: do you want *every* abandoned Draft gone (no save-and-resume, full stop), or just near-empty ones — e.g., someone who opened the wizard and immediately backed out at Step 0–1 with no real data entered? If it's the latter, the delete should be conditional (e.g., only auto-delete if nothing past contact info was ever filled in), not blanket.

**The "warn, then delete" mechanism has two genuinely different cases, and the browser constrains what's actually possible:**
1. **In-app navigation** (clicking another nav link, the browser back button while still in-app) — this is React Router's territory. `react-router-dom` is `^7.18.0` here (confirmed in `package.json`), which does support a real blocking hook (`useBlocker`) with a custom confirm UI — **but only under the data-router API** (`createBrowserRouter`/`RouterProvider`). This app's `AppRoutes.tsx` uses the older `<BrowserRouter><Routes>...</Routes></BrowserRouter>` pattern (confirmed, lines 1 and 18), which `useBlocker` does not work with. So either migrate `AppRoutes.tsx` to `createBrowserRouter` (a real infrastructure change affecting the whole app's routing, not just this page — flag and confirm before doing it) or handle in-app leaves manually: intercept clicks on the wizard's own step-navigation/back controls and the app's `Navbar` links while the wizard is active, and show your own custom confirm modal (following the app's existing `-overlay`/`-modal` markup convention) — this gets you the exact custom warning text from your example, since it's a component you control, not a browser dialog.
2. **Tab close / refresh / typed URL** — this is `beforeunload`'s territory, and it cannot show custom text in any current browser (Chrome, Firefox, Safari, Edge all ignore whatever string you set on `event.returnValue`/the event handler's return value and show their own generic "changes may not be saved" message). So the literal wording in your example ("If you leave this page, all your entered information will be lost") is only achievable for case 1 above, not case 2 — worth knowing so the spec doesn't over-promise. `beforeunload` can still trigger `event.preventDefault()` to show *a* warning, just not that exact text.

**Reliably deleting on unload is its own problem — recommend a background sweep as the real mechanism, not a client-side call.** A `beforeunload` handler cannot reliably await a `fetch` and have it finish before the tab actually closes. `navigator.sendBeacon()` is the standard "fire on unload" primitive, but it doesn't support custom headers — this app's whole API client convention is Bearer-token auth via a header, so `sendBeacon` doesn't fit without a special-cased exception (e.g., token in the body/query for just this one call). `fetch(url, { method: 'DELETE', keepalive: true, headers: {...} })` is a better technical fit (keeps the header-based auth pattern; `keepalive` lets the browser finish it after the page starts unloading) but still isn't guaranteed in every browser/scenario. **Given that, I'd treat immediate client-side deletion as a best-effort optimization, not the source of truth** — and add the actual reliability via a periodic backend sweep, following the existing precedent: `Program.cs` already registers a `DenylistCleanupWorker` as an `IHostedService` for exactly this kind of "clean up stale rows on a timer" job. A sibling worker that deletes Draft bookings past some age threshold (e.g., untouched for 24h) with no submission would make abandonment cleanup reliable regardless of whether the browser-side call fires, and is a small, convention-consistent addition.

**2b / 2c. Admin Bookings and Payments type filters — before building either, the four example categories need to be reconciled with what actually exists as data, because two of them aren't the same kind of thing.** `FoodDelivery` and `FullService` are real `BookingType` values today; `RentalService` would become a third real value only if item 1a above gets built. **"Plan by Budget" is not a data category at all** — it's a *creation method* (`Suggestionservice`'s `MaterializeAsync`, reachable from `PlanByBudgetTab` inside `CustomerDashboardPage.tsx`, behind the customer-only route guard) that produces an ordinary `FullService` or `FoodDelivery` booking, indistinguishable at the database level from one built through the normal wizard. There's no "origin"/"source" field anywhere recording how a booking was created. Filtering by "Plan by Budget" today is literally impossible — there's nothing to filter on.

**Two ways to resolve this, pick one:**
1. **Scope both filters to the real `BookingType` values only** (`FullService`, `FoodDelivery`, plus `RentalService` if 1a ships) and drop "Plan by Budget" as a filter category — it was likely included because it *feels* like a distinct booking flow from the customer's side, even though it isn't one at the data level.
2. **Add a real tracking field** — e.g., a nullable `BookingOrigin` (`Wizard`/`PlanByBudget`/`AdminWalkIn`, etc.) on `Booking`, set once at creation and never changed, giving both filters a genuine "Plan by Budget" bucket to query. This is a small, self-contained addition (one column, one migration, set in `CreateAsync`/`MaterializeAsync`) but it's new scope beyond what either task item currently asks for — confirm you actually want it before I write it into the build steps.

I'd lean toward option 1 unless the origin distinction matters for reporting beyond just these two filters, but this is a real fork — say which.
