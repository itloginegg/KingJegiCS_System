## 1. Backend Logic & Validation

**Double booking prevention — read `Bookingservice.cs` first, because what you're describing is today's intended design, not a bug.** I read it in full. `CreateAsync` deliberately does **not** check for overlapping schedules — the only place `CheckTimeSlotConflictAsync` (the real, buffer-expanded, overnight-aware overlap test) runs is inside `ConfirmBookingAsync` (via `EnsureTimeSlotAvailableAsync`, under a row lock on the calendar day) and as an advisory check before a payment (`EnsureDateStillAvailableAsync`). The comments in `ConfirmCoreAsync` spell out why: multiple customers can hold overlapping Draft/Pending bookings for the same date — nothing is exclusive until one of them pays the reservation fee and gets Confirmed, at which point the row lock enforces first-come-first-served and every other overlapping booking simply fails to confirm later. This is a real, common pattern for a catering business fielding multiple inquiries on a popular date before anyone commits money.

**Before building anything, confirm which of these you actually want:**
1. **Nothing changes** — this is working as designed, and what you saw was two Draft/Pending bookings coexisting, which is expected; the real guarantee is at Confirm, and it already works (I reviewed the overlap math and it's buffer-expanded and overnight-safe).
2. **Reject overlapping bookings at creation too** (a real, understandable ask if the goal is avoiding administrative clutter from many competing drafts) — this is a genuine policy change: it would remove the ability to hold interest from multiple parties on the same date before one commits. If this is what you want, add a `CheckTimeSlotConflictAsync`-style guard to `CreateAsync` (and `UpdateAsync`, since the date can change there too) — but decide first whether it should check against **Confirmed only** (matches today's actual scarcity model, just enforced earlier) or **Pending + Confirmed** (stricter — first Pending booking on a date blocks all others from even being created).

**Exception handling:** no new exception type is needed. `BookingRuleException` (in `Services/Bookingservice.cs`) is the single, established business-rule exception across the entire backend — every controller already catches it and returns `BadRequest(new { message = ex.Message })`, and every frontend API client already parses that `{ message }` shape into a typed error the UI displays (confirmed again while investigating this — see item 3's earlier note on this in a prior round). Whatever the new double-booking check ends up being, throwing `BookingRuleException` from it is sufficient and automatically wired end to end; there's nothing extra to build here.

## 2. Frontend Data Binding & Bugs

**Activity Log Mismatch — found the exact bug.** `CustomerDashboardPage.tsx`'s Overview "Activity"/"Recent Bookings" section (~line 1780–1782) reads:
```tsx
{EVENT_META[normalizeType(b.bookingType) as keyof typeof EVENT_META].icon}
...
{EVENT_META[normalizeType(b.bookingType) as keyof typeof EVENT_META].label}
```
It's normalizing `b.bookingType` — which is only ever `"FullService"` or `"FoodDelivery"` — instead of `b.eventType` (`"Wedding"`/`"Corporate"`/`"Birthday"`/`"Others"`). `normalizeType`'s matching logic (`includes('wed')`, `includes('birth')`, etc.) never matches either booking-type string, so it always falls through to its default return value, `'wedding'` — which is exactly why every row shows "Wedding Event" regardless of the real occasion. The correct usage already exists elsewhere in the same file for comparison — the "next event" card a few hundred lines up correctly does `normalizeType(nextBooking.eventType)`. **Fix:** change both occurrences to `b.eventType`.

One more thing worth fixing while you're in this exact code: `eventType` is always `null` for a `FoodDelivery` booking (by backend design — deliveries have no event type), so after the fix, delivery orders will fall through to the same `'wedding'` default and still misleadingly show "Wedding Event." Recommend branching on `b.bookingType === 'FoodDelivery'` first and showing something like "Food Delivery" for those rows, falling back to `normalizeType(b.eventType)` only for `FullService` bookings.
