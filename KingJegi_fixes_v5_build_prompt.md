**1b. PayMongo success redirect.** Good news: this is very likely a **configuration gap, not a code bug** — the frontend side is already fully and correctly built. `PaymentReturnPage.tsx` exists, `AppRoutes.tsx` already routes `/payment/success` and `/payment/cancel` to it, `CustomerDashboardPage.tsx` already stashes `{invoiceId, paymentId}` into `sessionStorage` before redirecting to checkout (~line 585), and the return page correctly handles the real subtlety here — arriving on `/payment/success` isn't proof of payment, since the browser redirect and PayMongo's webhook are two separate, unordered round-trips — by listening for the `PaymentHub`'s `"PaymentUpdated"` broadcast with a polling fallback before declaring success and routing into `/dashboard?tab=payments`. This is solid, already-working code.

The reason it's not firing is almost certainly that **`PayMongo:SuccessUrl`/`PayMongo:CancelUrl` were never set** in this environment. `PayMongoOptions.cs` defaults both to `string.Empty`, and `Paymongoservice.cs` turns a blank value into `null` before sending the checkout-session request — meaning PayMongo has nowhere to send the browser back to, and it just sits on its own hosted confirmation page after payment. That matches "stuck on the PayMongo page" exactly. **Fix:** set, via `dotnet user-secrets set` from `BackEnd/System_ApiTest`:
```
PayMongo:SuccessUrl = http://localhost:5173/payment/success
PayMongo:CancelUrl  = http://localhost:5173/payment/cancel
```
(5173 confirmed as the configured Vite dev port in `vite.config.ts` — adjust if deploying anywhere else.) No code change should be required; re-test after setting these. If it's still broken afterward, check next whether `Paymongoservice.CreateCheckoutSessionAsync` is actually including `success_url`/`cancel_url` in the request it sends (it does, conditionally on the config being non-blank — so this really should just be the missing secret) and whether PayMongo's own dashboard requires redirect URLs to be pre-registered.

3. Hit the exact reported URL directly (curl, or the browser's network tab) with the backend confirmed running, and read the real HTTP status — don't trust the rendered error page's wording alone.
4. Only if that turns up a genuine 404: re-verify the running process's content root actually matches the project folder (relevant if launched from an unusual working directory).

Given everything reviewable checks out, this is more likely an environment/runtime issue than something to patch in source — but if live testing turns up a real code-level cause, it won't be one of the textbook ones (missing `UseStaticFiles()`, wrong middleware order, wrong port), since those are all confirmed fine.
