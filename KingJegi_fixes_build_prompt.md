## 1. "Plan by Budget" booking parity

**Root cause, verified — this is a frontend gap, not a backend bug.** `Services/Suggestionservice.cs`'s `MaterializeAsync` is *supposed* to only create a Draft booking (that's the documented design: "Suggestions are stateless — nothing is persisted until materialize is called," and the Draft is left "fully editable, so the customer can review... and confirm"). An Invoice is only ever generated by `Bookingservice.SubmitAsync` → `Invoiceservice.GenerateAsync`, when a Draft moves to Pending. That part is working as designed.

The actual gap: nothing in the frontend ever calls Submit for a Plan-by-Budget booking. Compare the two flows:
- `BookingPage.tsx`'s standard wizard calls `submitBooking(session.token, bookingId)` (from `api/bookingApi.ts`) as its Step 4 finale (~line 383) — this is why a normal booking ends up Pending with a real Invoice.
- `CustomerDashboardPage.tsx`'s `PlanByBudgetTab.materialize()` (~line 746) calls `materializeProposal`, then hands the result to `handlePlanMaterialized` (~line 1351), which only does `setTab('bookings'); setDetailBooking(booking); fetchDashboard()`. It never calls `submitBooking`. The Draft just sits there.

It gets worse: `BookingDetailModal` (the modal that opens right after materializing) has **no Submit action for any Draft booking at all**, regardless of how it was created. So this isn't only a Plan-by-Budget problem — any Draft that didn't come from the full `BookingPage` wizard currently has no in-dashboard way to advance to Pending.

**Fix — confirm placement before building:**
1. **Recommended:** add a "Submit Booking" button to `BookingDetailModal` whenever `booking.status === 'Draft'`, calling the existing `submitBooking()` client function. This fixes the gap for every Draft-origin booking uniformly, not just budget-created ones.
2. **Alternative:** auto-submit immediately after a successful `materializeProposal`, mirroring the wizard's automatic last step. This removes a manual review step the wizard currently gives customers before submitting — a real UX call, not just plumbing, so don't pick this silently.

Either way, once Submit is wired in, verify `getInvoiceByBooking`, `getPaymentSchedule`, and `getPaymentsByInvoice` (already imported in `CustomerDashboardPage.tsx`) return real data for a budget-created booking exactly as they do for a wizard-created one — no backend change should be needed here, only the missing frontend call.

## 2. Virtual assistant chat widget

**Current state, verified — there are two separate assistant surfaces today, and only one is real.** `components/landing/ChatWidget.tsx` is already mounted globally — it's imported into `BookingPage.tsx`, `CustomerDashboardPage.tsx`, `LandingPage.tsx`, `MenuPage.tsx`, `PackagePage.tsx`, and `RentalsPage.tsx` — but it's still the original static teaser: a bubble that links to `/#availability`, no backend call of any kind. Separately, `CustomerDashboardPage.tsx`'s `MessagesTab` (~line 967) is the one that's actually wired to the real assistant — it calls `sendChat`/`listConversations`/`getConversation` from `api/assistantApi.ts` and renders proposals via `ProposalCard` — but it only exists inside the dashboard's "Messages" sidebar tab (`NAV_ITEMS`/`Tab` type, ~line 1106).

**Refactor:**
- Retire `MessagesTab` and the `'messages'` entry from `CustomerDashboardPage`'s `Tab` type and `NAV_ITEMS` (~lines 1106–1112), including the unread-dot state (`messagesUnread`) tied to it.
- Move `MessagesTab`'s real wiring — conversation load-on-open, `sendChat`, proposal rendering — into an upgraded `ChatWidget.tsx`, so the one component already mounted everywhere becomes the one real assistant surface, floating on every page rather than living inside one dashboard tab.
- The widget now needs to handle two states, since it's mounted on public pages too: **logged out** → since `AssistantController` is `[Authorize(Roles = "Customer")]` with no anonymous path, keep something like the current static teaser or a "sign in to chat" prompt; **logged in as Customer** → the real chat, reusing `assistantApi.ts` unchanged.

**New requirements needing a decision before building — these are scope calls, not wiring:**
- **Animated avatar.** Nothing in the current stack (`lucide-react`, `framer-motion`, static assets) provides a character avatar. Confirm the approach before building: a Lottie/JSON animation, a CSS/SVG idle+talking loop, or a looping video clip are all viable and very different amounts of work — state which one and get sign-off.
- **Voice interaction.** No STT/TTS library exists in `package.json` today. The low-cost path is the browser's built-in Web Speech API (`SpeechRecognition` for input, `SpeechSynthesis` for reading replies aloud) — zero new dependencies, feeds straight into the existing `sendChat` call and reads the existing `reply` string, but has real gaps in browser support (weak/absent on Firefox, inconsistent on mobile). A higher-fidelity dedicated STT/TTS provider would need a new backend integration entirely outside Slice C's current scope. Recommend starting with Web Speech API plus a graceful text-only fallback when it's unavailable — confirm before building since this affects how much of "voice interaction" actually ships.
- Keep the existing styling convention: `ChatWidget.tsx` already uses inline `style={{}}` objects referencing `var(--surface)`/`var(--accent)`/`var(--shadow-lg)`/etc. — extend that pattern rather than introducing Tailwind classes or a separate stylesheet.

## 3. Food delivery flow refactor — move to MenuPage as cart + checkout

**Important precondition, verified:** `MenuPage.tsx` is currently, by its own header comment, "Static content — design reference only, no backend calls." Its `DISHES`/`CATEGORIES` arrays are hardcoded with small numeric ids that don't correspond to any real `Menuitem`/`Menutray` database GUID. It does already have a lightweight cart-shaped feature — a `plan: Record<number, number>` state plus a bottom `mnu-plan` summary bar with a "Clear" button and a static CTA link — which is a good visual starting point, but the whole page needs to be connected to the real catalog before any checkout can work; this is a bigger lift than "add a cart to an existing shopping page."

**Fix:**
1. Replace the static `DISHES`/`CATEGORIES` arrays with real data from the backend catalog: `GET /api/MenuItems` and `GET /api/MenuTrays` (both `[Authorize]`-only — any authenticated role, not admin-restricted, per `MenuitemsController`/`MenutraysController`).
2. Evolve `plan` into a real cart keyed by each line's real GUID **and** its type (`MenuItem` vs `MenuTray` — both are orderable for delivery), storing quantity per line.
3. Build a checkout step/page that collects exactly what `Bookingservice.CreateAsync` requires for `bookingType: 'FoodDelivery'`: `eventDate` (delivery date), `startTime` (delivery time), `venueAddress` (delivery address), optional `contactNumber` — no package, no end date/time, no event type, no guest count, matching `BookingCreatePayload` for that type. Then call `createBooking`, followed by the per-line add calls for each cart entry (mirror the pattern `BookingPage.handleSaveSelections` already uses for menu items/trays — confirm the exact exported function names in `bookingApi.ts` before wiring), then `submitBooking` to reach the same parity fixed in Section 1.

**Decision to confirm before building:** does browsing require login? The real catalog `GET` endpoints need *some* authenticated JWT, but `/menus` is currently a public route (outside `ProtectedRoute` in `AppRoutes.tsx`), meant for anonymous visitors. Recommended: keep browsing anonymous (either via a new public read endpoint, or by continuing to show cached/static catalog data to logged-out visitors) and only require login at the "add to cart" or checkout step — `createBooking` needs a real `customerId` from the JWT regardless, so login is unavoidable there either way. This mirrors typical e-commerce UX but is a product decision — confirm before choosing, don't default silently.

Once this lands, remove the `'menu'` service-flow entirely from `BookingPage.tsx`: the `pickService('menu')` card in the Step-0 picker, its `'Delivery Details'`/`'Menu & Add-ons'` step labels and gated fields, and the `bookingType === 'FoodDelivery'` branch of `handleCreateBooking` this flow drove. See Section 4 for what's left in the wizard after this.

## 4. Rental items UI — the actual bug

**Root cause, verified.** `BookingPage.tsx`'s Step-0 "Rental Items Only" card (`pickService('rentals')`, ~line 563) sets `serviceFlow = 'rentals'`. But `handleCreateBooking`'s payload (~line 282) computes `bookingType: serviceFlow === 'event' ? 'FullService' : 'FoodDelivery'` — so the rentals-only flow creates a `FoodDelivery` booking. When Step 3 then calls `addRental(token, bookingId, rentalItemId, quantity)` → `POST /api/Bookings/{id}/rentals` → `Rentalservice.AddRentalAsync` → `Bookingservice.EnsureNotDeliveryAsync`, the backend throws `"Food delivery orders can only contain menu items and trays."` **every single time**, because rentals are only ever permitted on a `FullService` booking, by design. This flow is broken today for anyone who reaches Step 3 and tries to add a rental — this is "the specific backend endpoint" the constraint is pointing at, and it's a real, reproducible bug, not a style mismatch.

**The fix is a data-binding/logic fix, not a backend change and not a redesign:** the "Rental Items Only" flow must create a `FullService` booking, since that's the only type `AddRentalAsync` will accept. That means its Step 2 (currently a "Delivery Details" form — date/time/address only) needs to collect what `CreateAsync` requires for `FullService`: end date, end time, event type, and guest count — the same fields the `'event'` flow already collects. Keep the visual layout, the `bk-` prefixed classes, the pipeline stepper, and the rentals-selection UI in Step 3 (~line 894) exactly as they are — none of that needs to change, only which booking type the flow targets and which fields Step 2 asks for.

**Sequencing note:** do Section 3 before this one, or resolve both together. Once Food Delivery is fully out of `BookingPage` (Section 3), the wizard's Step-0 picker naturally reduces to two real paths — `'event'` (full package + menu) and `'rentals'` (add-ons only, no package/menu) — both `FullService` under the hood. Fixing `'rentals'` in isolation, before Food Delivery is removed, still leaves a confusing three-way picker where two of the three cards produce a `FoodDelivery` booking type for different reasons.
